# AI 키캡 누르기 인터랙션 — 기획 핸드오프

**작성일** 2026-08-08 · **브랜치** `feature/keycap-press` (origin/main 기반)

> 이 문서는 **기획 결정과 근거만** 담는다. 세부 구현 계획은 별도 세션에서 이 문서를 읽고 작성한다.
> 컴포넌트 시그니처·테스트 케이스·파일 구조는 여기서 정하지 않았다. 다만 **이미 결정된 것을 다시 논의하지 않도록**
> 무엇을 왜 골랐는지, 무엇을 왜 버렸는지는 최대한 자세히 남긴다.

## 한 줄 요약

생성된 AI 키캡 이미지를 **누르면 실제 키캡처럼 눌리고 기계식 키보드 소리가 나게** 한다. 사용자 피드백에서 나온 아이디어다.

## 왜 하는가

이 기능의 목적은 "재미"보다 **공유 링크 방문자의 전환**이다. `/figurines/share`에 링크를 타고 들어온 비로그인 방문자는
남의 반려동물 키캡을 구경하러 온 사람이지 서비스를 쓰러 온 사람이 아니다. 만져볼 게 있어야 "나도 만들어보기"로 넘어간다.
따라서 **결과 화면보다 공유 페이지가 더 중요한 적용 지점**이다.

## 검토 후 버린 것 — 다시 제안하지 말 것

**진짜 레이어 분리 (사진 속 갈색 키캡만 움직이기)**
결과물이 평면 PNG 한 장이라 브라우저는 키캡의 경계를 알 수 없다. 실현하려면 백엔드가 알파 채널 컷아웃을 하나 더 내려줘야 한다.
브라우저 실시간 배경 제거도 검토했으나 기각 — 성능 좋은 RMBG-1.4/2.0은 **비상업 라이선스**라 서비스에 못 쓰고,
MIT인 BiRefNet은 모델이 수십 MB다. 재미 하나에 40MB 다운로드는 말이 안 된다.
**추가 근거:** 생성 결과물은 피사체가 프레임을 거의 꽉 채운다(강아지 머리 위쪽 8%, 키캡 바닥 아래쪽 95%).
전체를 움직이는 것과 피사체만 움직이는 것의 차이가 작고, 액자를 고정하면 위화감이 대부분 사라진다.
백엔드 의존을 붙이는 순간 일정이 남의 손에 넘어간다는 실무적 이유도 있다 —
AI 키캡 배지에 쓰는 `aiGenerated` 플래그도 백엔드에 요청해뒀지만 값이 전부 `false`로 내려와 운영에서 배지가 안 보이는 상태가 이어졌다.
같은 리스크를 재미 기능에 또 걸 이유가 없다.

**축 랜덤 배정 / 뽑기**
"소리가 꺼져 있어도 배지는 보이니 기능이 안 사라진다"가 유일한 장점이었는데, **축 목록을 그냥 화면에 띄우면 그게 더 잘 해결된다**.
장점이 대체되면 단점만 남는다 — 해시 로직, 첫인상 품질 통제 불가(누군가는 제일 시끄러운 축으로 이 기능을 처음 만난다), 상태 동기화.

**연타할 때마다 소리 바꾸기 (round-robin)**
kbsim이 축마다 행별로 따로 녹음해둬서 기술적으로 가능하고 실제로 효과도 있었지만, 사용자 판단으로 제외.
*이 결정이 음원 출처 선택을 바꿨다* — round-robin이 MIT 세트를 고른 주된 근거였다.

**무접점(Topre)**
두 출처 모두 품질 미달. CC0는 빠른 연속 타이핑에서 억지로 잘라 앞뒤 잔향이 깔리고, MIT는 원본이 −28dBFS라 증폭 잡음이 생긴다.
Topre CC0 녹음 자체가 세상에 열 개도 안 된다. 게다가 원래 조용한 축이라 "조용해서 안 들리는 건지 녹음이 나빠서인지" 사용자가 구분 못 한다.

**WebAudio 합성음**
초기 프로토타입은 노이즈 버스트를 필터링해 합성했다. 번들 0KB라는 장점이 있었지만 실제 녹음과 비교가 안 됐다.

**피드 카드/상세 적용 · 누른 횟수 카운트** — 범위 밖.

## 반드시 알아야 할 제약

**1. 결과물은 평면 PNG 한 장이다**
`job.resultImageUrl` 하나뿐이라 이미지 안의 요소를 따로 움직일 수 없다. 위 "버린 것" 첫 항목의 배경.

**2. 자가 시연은 소리를 낼 수 없다**
브라우저 자동재생 정책상 사용자 제스처 전에는 `AudioContext`가 `suspended`다. 막으려고 애쓰는 게 아니라 **애초에 못 낸다**.
따라서 `AudioContext`는 첫 `pointerdown` 안에서 lazy 생성해야 한다. 페이지 로드 시 만들면 첫 소리를 놓친다.

**3. iOS 무음 스위치를 켜면 WebAudio도 안 들린다**
한국 아이폰 사용자 상당수가 무음 모드로 다닌다. **우리가 고칠 수 없다.** 이 사람들에게 축 기능은 존재하지 않는다.
소리에만 의존하는 설계를 하면 안 되는 이유이고, 축 칩 목록을 화면에 노출하기로 한 이유이기도 하다.

**4. 정렬 `transform`과 둥둥 `transform`은 충돌한다**
힌트 배지를 중앙 정렬하려면 `-translate-x-1/2`가 필요한데 `badgeFloat`도 `transform: translateY()`를 쓴다.
같은 요소에 둘 다 걸면 애니메이션이 정렬을 덮어써서 배지가 왼쪽으로 튕겨나간다.
**바깥 요소가 정렬, 안쪽 `AiKeycapBadge`가 둥둥**을 맡아야 한다.

**5. 공유 페이지의 `DetailImage` 폴백을 깨뜨리지 말 것**
`/figurines/share`는 `DetailImage`를 쓴다 — 800 웹피 썸네일 우선, 없으면 원본 폴백(생성 직후엔 Lambda 썸네일이 아직 없다).
누름 기능을 `<img>`를 직접 렌더하는 컴포넌트로 만들면 이 폴백이 통째로 날아간다.
**children을 감싸는 래퍼 형태**여야 두 페이지가 각자의 이미지 컴포넌트를 유지할 수 있다.
또한 share 페이지는 서버 컴포넌트라 클라이언트 경계가 필요하다.

## 유도(넛지) 명세 — C안

세 가지를 만들어 비교했고 사용자가 **C(둘 다)** 를 선택했다.

- **자가 시연** — 결과 등장 0.9초 뒤 키캡이 스스로 한 번 눌렸다 올라온다. 4.2초 뒤 한 번 더 하고 멈춘다. 소리는 안 난다(제약 2).
- **물결** — 키캡 중앙에서 원이 계속 퍼진다. 첫 누름까지 멈추지 않는다.
- **배지** — `AiKeycapBadge label="눌러보기" floating`, 키캡 하단 중앙.

**한 번이라도 누르면 셋 다 영구히 사라진다.** `localStorage`에 기록해 다음 방문에도 뜨지 않게 한다.

> **기획 시 제기됐던 우려(참고용, 결정은 C로 확정됨):** 물결이 자랑 결과물인 사진 한가운데를 계속 가리고, 안 누르는 사람에겐
> 영원히 돈다는 점. 배포 후 거슬린다는 반응이 나오면 물결만 먼저 떼어내는 게 가장 손쉬운 되돌리기다.

## 접근성 요구사항

- 이미지를 누르는 구조라 키보드 접근이 안 된다 — 버튼 역할 부여와 Space/Enter 처리가 필요하다.
- `prefers-reduced-motion: reduce`면 스쿼시·자가 시연·물결·배지 둥둥을 모두 끈다. **소리는 유지한다**(모션 민감성과 소리는 별개).
- 소리가 기본 켜짐이므로 음소거 버튼은 반드시 눈에 띄는 위치에.

## 남은 열린 항목

1. **박스 제이드 클립이 252ms로 유독 길다.** 다른 축은 60~90ms. 빠르게 두 번 누르면 소리가 겹친다.
   구현 시 실제로 들어보고 거슬리면 끝을 잘라 페이드아웃 처리한다.
2. **공유 페이지에서 축 칩이 전환율을 해치는지.** 이 페이지의 유일한 CTA("나도 만들어보기") 위를 칩 줄이 차지한다.
   "만져볼 거리가 체류를 늘린다"는 쪽에 걸었지만 검증되지 않은 가설이다. 배포 후 공유 페이지 → `/figurines/new` 클릭률로 확인 가능.
